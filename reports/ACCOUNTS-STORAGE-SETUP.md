# Аккаунты, разделение доступа и SQLite

Реализовано 31 октября 2026 года. Этот этап заменяет ограничения «одна организация / JSON» из предыдущих отчётов. Подключение реальной оплаты отложено по указанию пользователя.

## Что доступно

- Регистрация по email и паролю от 12 до 128 символов, вход, выход, восстановление сеанса после перезагрузки страницы.
- Отдельная организация каждого аккаунта, собственные ключи API, история проверок, настройки и список заказов.
- Изменение названия организации и смена пароля с отзывом прежних сеансов.
- Бесплатный анализ SQL по-прежнему доступен гостю; проверка из кабинета записывается в историю его организации.
- API-ключ принадлежит конкретной организации. Поля organizationId/id из пользовательского запроса не определяют права доступа.
- Ключи API показываются полностью только при создании. В SQLite сохраняются хеши; проверка ключа не расходует счётчик анализа.

Исполнитель входит в прежний основной профиль через «Администратор» с LOCKGUARD_ADMIN_TOKEN. Новая регистрация не захватывает этот профиль и его старые данные. Клиенту администраторский токен не нужен.

## Запуск

Нужен Node.js 24+. Для новой установки скопируйте .env.example в .env; существующее окружение не перезаписывайте.

```sh
npm ci --ignore-scripts
npm start
```

Откройте http://localhost:3000 и кнопку «Войти» или «Регистрация». В production обязательно задайте APP_URL с HTTPS, настройте TLS на вашем сервере и используйте тот же адрес в браузере. В production cookie имеет Secure и префикс __Host-. GitHub Pages остаётся статической демонстрацией: там нет API аккаунтов.

LOCKGUARD_ALLOW_REGISTRATION=false отключает новую регистрацию, сохраняя вход действующих пользователей. За доверенным reverse proxy укажите точные адреса своего прокси в LOCKGUARD_TRUST_PROXY_IPS; только от этих адресов учитывается последний X-Forwarded-For. Без этого ограничения попыток входа применяются к сетевому адресу прямого соединения.

Пароли хешируются scrypt (N=32768, r=8, p=3) с отдельной случайной солью. Одновременно допускаются два вычисления хеша; переполнение возвращает 429. Ограничения попыток входа хранятся в SQLite и сохраняются после перезапуска. В браузере используется HttpOnly / SameSite=Lax cookie со сроком 7 дней; в БД хранится только хеш непрозрачного токена. Cookie не передаётся через localStorage. Смена пароля сверяет исходный хеш в транзакции, чтобы незавершённый вход по старому паролю не создал новый сеанс после смены.

Запросы изменения данных проверяют Origin и тип JSON; глобальный CORS * удалён. Интерфейс очищает приватные данные при выходе, игнорирует задержавшиеся ответы прежнего аккаунта и обновляет состояние входа в других вкладках через BroadcastChannel.

## Данные и перенос

По умолчанию SQLite находится в data/lockguard.sqlite3. LOCKGUARD_DB_FILE позволяет выбрать другой путь. Если задан старый путь с окончанием .json, SQLite создаётся рядом, с расширением .sqlite3.

Перед переходом остановите прежний сервер, записывающий JSON. При первом открытии импортируются профиль, ключи с прежними ID, история и платёжный журнал; известный демонстрационный ключ отзывается. Повторный запуск не повторяет импорт. Исходный JSON не изменяется; создаётся отдельная копия .pre-sqlite-UUID.bak. Эти старые файлы могут содержать прежние секреты: доступ к ним ограничивается правами файлов, хранить их следует закрыто.

Таблицы разделены по организациям, связи проверяются внешними ключами, значения передаются через параметры SQL. Операции аккаунтов, счётчики и прежние подтверждения платежей сохраняются транзакционно. Два процесса читают актуальные записи, а не перезаписывают снимки памяти.

Используется журнал DELETE и synchronous=FULL. В установленном Node.js 24.12 SQLite имеет версию 3.50.4; для неё upstream описывает редкий дефект WAL-reset при конкурентных соединениях. Выбран режим без WAL. Это сохраняет транзакции, но конкурентные читатели и писатели могут ожидать освобождения блокировки; ожидание ограничено 5 секундами. SQLite рассчитана на один сервер и локальный диск. Для нескольких хостов потребуется серверная БД.

## Резервные копии

HTTP-сервер проверяет возраст последней копии при запуске и затем делает копию раз в LOCKGUARD_BACKUP_HOURS часов (по умолчанию 24). Каталог LOCKGUARD_BACKUP_DIR по умолчанию data/backups. Хранится LOCKGUARD_BACKUP_RETENTION последних копий (по умолчанию 7, диапазон 1–100).

Копия создаётся SQLite backup API, проверяется integrity_check и foreign_key_check. Только после успешной проверки обновляется время последней копии и выполняется ротация файлов с собственным префиксом lockguard-backup-. Ошибка выводится в журнал сервера; приложение не сообщает об успешной копии при сбое.

Разовая копия использует .env:

```sh
npm run backup
```

Восстановление:

```sh
npm run restore -- data/backups/FILE.sqlite3 data/restored.sqlite3
```

Замените FILE.sqlite3 реальным именем. Команда проверяет копию и создаёт только новый файл. Она отказывается перезаписывать существующую БД и отзывает все браузерные сеансы в восстановленном файле. Пароли, организации, ключи и история сохраняются. После остановки сервера задайте LOCKGUARD_DB_FILE=data/restored.sqlite3 и запустите его снова.

Автоматической отправки данных во внешние сервисы нет. Для защиты от отказа диска нужен отдельный защищённый носитель или ваш процесс внешнего копирования. Копии содержат приватные сведения и хеши паролей; их нельзя публиковать или класть в каталог сайта.

## Проверки и оставшиеся ограничения

Полный локальный прогон: 184/184 теста, включая 20 новых сценариев аккаунтов, интерфейса и хранения. Проверяются две организации через HTTP, запрет чужого отзыва ключей и подмены organizationId, CSRF, хеши, ограничение входа, отзыв сеансов, конкурентные записи, перенос журнала оплаты, откат при ошибке, целостность и восстановление копии, очистка интерфейса и задержавшиеся ответы.

Подтверждение email и восстановление пароля по почте не подключены. Командные приглашения и несколько пользователей внутри одной организации не реализованы. У каждого нового аккаунта собственная организация. Полный контроль платных возможностей и самостоятельная оплата клиентами остаются отдельной работой; реальные платежи, возвраты и внешняя отправка резервных копий на этом этапе не выполнялись.
