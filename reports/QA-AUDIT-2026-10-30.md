## Изменения настройки и поведения

1. Установить длинный случайный `LOCKGUARD_ADMIN_TOKEN` в окружении сервера или локальном `.env`. Шаблон добавлен в `.env.example`; существующий `.env` не изменялся.
2. Перезапустить сервер. В dashboard использовать **Admin sign in / out**. Токен хранится только в памяти страницы и сбрасывается при перезагрузке. Для программного доступа передавать `Authorization: Bearer <token>`.
3. Анализ SQL, каталог правил, split и simulate остаются публичными. Watchdog API по-прежнему демонстрирует фиксированную телеметрию; это не живой мониторинг.
4. Checkout теперь сообщает об ожидании подтверждения оплаты. Автоматическое включение подписки не реализовано.
5. Миграции с SET LOCAL вне явного BEGIN теперь получают LG-008. Если транзакцией управляет ORM, передавать для проверки SQL с соответствующим BEGIN/COMMIT.

## Открытые проблемы и приоритет следующего этапа

### P1 — неполное понимание SQL

Парсер построен на собственном разборе и регулярных выражениях; он не является полным PostgreSQL AST-парсером. Воспроизведён ложный PASSED для:

```sql
SET lock_timeout=3000;
DO $$ BEGIN EXECUTE 'DROP TABLE users'; END $$;
```

Такой блок дополнительно ошибочно помечается как DML-only. Нужны явное обозначение неподдерживаемых конструкций и отказ от вердикта безопасности при неполном разборе, затем интеграция полноценного парсера. Обработка savepoint, динамического SQL и всех форм транзакций не покрыта текущей моделью LG-008.

Контекст новых таблиц собирается по всему файлу и может переноситься между файлами; он не доказывает реальный порядок применения миграций и текущее состояние БД. Проверки наличия индексов тоже не заменяют изучение действующей схемы. Эти ограничения требуют отдельного пересмотра модели контекста.

### P1 — AutoSplitter остаётся генератором черновиков

Исправлены конкретные потери типа и определения индекса, но генератор работает по нарушениям, не переносит весь исходный SQL и местами предполагает имена/типы/ссылку на id. ORM-шаблоны не проверены выполнением. Сгенерированные фазы нельзя считать автоматически эквивалентной или гарантированно безопасной заменой миграции. Нужны полноценный AST, сохранение всех операций и тесты на реальной БД.

### P1 — интеграции и хранение

- Счёт содержит фиксированные демонстрационные реквизиты. Это шаблон, требующий настройки владельцем; настоящая платёжная интеграция и проверяемое подтверждение оплаты отсутствуют.
- GitHub webhook не получает реальные изменённые файлы и не публикует статус PR. Теперь он явно отклоняет реальные события вместо выдачи демонстрационного результата.
- Ключи лежат в JSON в открытом виде, начальный ключ имеет известное значение при отсутствии DEFAULT_API_KEY. Для реального сервиса нужны хеши ключей, безопасный bootstrap и разграничение организаций/ролей.
- JSON-хранилище подавляет ошибки чтения/записи и не обеспечивает согласование нескольких процессов. Нужны явные ошибки сохранения и подходящее транзакционное хранилище.

### P2 — согласованность и эксплуатация

- `docs/lockguard-engine.js` — отдельная браузерная реализация; исправления серверного ядра автоматически в неё не попадают. Статический playground требует отдельной синхронизации и тестов.
- Утверждения интерфейса о «100% safe» и гарантированном downtime сильнее возможностей статического анализатора. Симуляция — оценочная модель, не фактический replay нагрузки.
- Нужны ограничения частоты запросов и тестирование нагрузки перед публичным развёртыванием.
- Версии package.json/CLI и счётчик тестов README расходятся. Существующий workflow публикует результат безопасного fixture, а не аудит SQL конкретного PR.

## Что проверялось

- `node --test`: 120 тестов, 120 успешных; CLI E2E, правила, парсер, API, smoke и новые негативные сценарии.
- HTTP-регрессии: битый JSON/URL, отсутствие авторизации, административный доступ, попытка бесплатной активации, неизвестный API, неверные типы и UTF-8 payload свыше 1 MiB; после ошибок сервер отвечает на следующий запрос.
- Проверены отзыв ключа, уникальность истории после 130 записей, экранирование счёта, передача DATABASE_URL аргументом, ошибочная git revision, SQL-рекомендации и timeout scope.
- `node --check src/ui/app.js`, `git diff --check`.
- Серверные тесты перенаправлены на временные БД, чтобы последующие прогоны не меняли пользовательскую историю.

Реальная PostgreSQL, платежи, Telegram API, GitHub API и визуальные сценарии браузера не проверялись. Публикация, отправка сообщений и развёртывание не выполнялись. Команда npm.ps1 блокировалась политикой PowerShell, поэтому использован эквивалентный `node --test`. Для HTTP-тестов потребовался запуск вне песочницы из-за EACCES на 127.0.0.1.

Семантика таймаутов сверена с [PostgreSQL: lock_timeout](https://www.postgresql.org/docs/18/runtime-config-client.html) и [PostgreSQL: SET](https://www.postgresql.org/docs/current/sql-set.html): нулевое значение отключает timeout; SET LOCAL ограничен текущей транзакцией и вне неё не действует.
