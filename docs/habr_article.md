# Как безобидный ADD COLUMN положил наш продакшен на 43 минуты (и почему Postgres 11+ вас не спасет)

Четверг, 14:15. До планового созвона с бизнесом оставалось сорок минут. Наш мидл-разработчик накатил в стейджинг короткий Pull Request: нужно было добавить колонку с датой активации фичи в таблицу заказов `orders`. 

Одна строчка в DDL:
```sql
ALTER TABLE orders ADD COLUMN activated_at TIMESTAMP DEFAULT now() NOT NULL;
```

Код-ревью пройдено за три минуты. В стейджинге миграция применилась за 12 миллисекунд. CI позеленел. Кнопка «Merge» нажата, пошел деплой в прод.

Ровно через 18 секунд в корпоративном Slack взорвался канал `#alerts-critical`:
* PagerDuty: `Latency p99 > 15 000ms [CRITICAL]`
* Nginx: `HTTP 504 Gateway Timeout spike: 94.2%`
* PgBouncer: `server_login_retry: connection pool exhausted (max_connections = 300 reached)`

Продакшен e-commerce платформы с 30 миллионами заказов и дневным оборотом в сотни тысяч долларов перестал принимать оплату и оформлять корзины. Ближайшие 43 минуты превратились в лихорадочный пожар с дропом коннектов, ручным киллом PID в `pg_stat_activity` и холодным потом на спине.

В этой статье я расскажу:
1. Почему миф «в PostgreSQL 11+ добавление колонок с DEFAULT стало мгновенным» убивает базы данных.
2. Что такое **Head-of-Line Blocking** в очереди блокировок Postgres и почему медленный `SELECT` в связке с быстрым DDL гарантированно роняет сервис.
3. Как правильно писать zero-downtime миграции (готовые SQL-паттерны).
4. Как мы навсегда решили эту проблему у себя, написав открытый AST-гейткипер **LockGuard**, который блокирует такие PR еще на этапе CI/CD.

## 1. Анатомия катастрофы: Что на самом деле произошло в ядре Postgres?

В Postgres 11 действительно появилась отличная оптимизация: если вы добавляете колонку с *константным* значением (например, `DEFAULT 'active'`), Postgres не перезаписывает таблицу на диске, а просто записывает метаданные в системный каталог `pg_attribute` (`atthasmissing = true`, `attmissingval`).

Но дьявол кроется в двух вещах: **типе выражения** и **очереди блокировок**.

### Ловушка №1: Volatile-функции
Разработчик написал:
```sql
DEFAULT now()
```
Функция `now()` (или `gen_random_uuid()`, `clock_timestamp()`, `random()`) в терминах PostgreSQL является **volatile**. Это значит, что для каждой строки таблицы значение должно вычисляться заново! 

Оптимизация каталога здесь отключается. PostgreSQL обязан:
1. Заблокировать таблицу.
2. Прочитать 30 миллионов строк с диска в память.
3. Вычислить `now()` для каждого кортежа (tuple).
4. Переписать страницу данных на диск.
5. Перестроить сопутствующие структуры.

На нашей таблице в 45 ГБ эта операция в фоне занимала около 8 минут. Но даже если бы это длилось всего 3 секунды, нас убило не это. Нас убила **очередь блокировок**.

### Ловушка №2: Очередь блокировок и Head-of-Line Blocking

Любой `ALTER TABLE` требует эксклюзивной блокировки самого высокого уровня — **`ACCESS EXCLUSIVE`**. 

`ACCESS EXCLUSIVE` конфликтует абсолютно со всеми другими операциями: не только с `INSERT`, `UPDATE` или `DELETE`, но и с обычным безобидным `SELECT` (который берет `ACCESS SHARE`).

А теперь посмотрите, как устроена очередь в диспетчере блокировок PostgreSQL:

```
[Пользовательский трафик: SELECT * FROM orders WHERE user_id = 42 (длится 4 секунды)]
                                   │
                                   ▼
[Миграция: ALTER TABLE orders ADD COLUMN ... — запрашивает ACCESS EXCLUSIVE]
┌─────────────────────────────────────────────────────────────────────────────┐
│ Postgres Lock Manager: "Таблица занята SELECT'ом. ALTER TABLE встает ждать".│
└─────────────────────────────────────────────────────────────────────────────┘
                                   │
                                   ▼
[Новые входящие SELECT'ы от API: 250 запросов в секунду по 2мс каждый]
┌─────────────────────────────────────────────────────────────────────────────┐
│ Postgres Lock Manager: "Стоп! В очереди УЖЕ ЖДЕТ запрос с ACCESS EXCLUSIVE. │
│ Ни один новый SELECT/INSERT/UPDATE не будет запущен, пока не пройдет DDL!"  │
└─────────────────────────────────────────────────────────────────────────────┘
```

Это фундаментальный принцип планировщика Postgres: **запрос с исключительной блокировкой имеет приоритет ожидания**, чтобы транзакции DDL не голодали вечно.

Но на продакшене с постоянным потоком запросов происходит следующее:
1. `ALTER TABLE` встает в очередь за одним «зазевавшимся» аналитическим SELECT.
2. Все следующие тысячи клиентских запросов встают **за ним**.
3. PgBouncer забивает весь пул `max_connections` за 4 секунды.
4. Все микросервисы получают `Connection refused` или отваливаются по таймауту.
5. Сервер приложений захлебывается, Nginx плюется 504 ошибками.

Вот так «мгновенная» миграция положила весь бизнес на 43 минуты.

## 2. Три смертных греха миграций в PostgreSQL (и их безопасные альтернативы)

После инцидента мы провели жесткий аудит и выделили 3 главных антипаттерна, которые регулярно проскакивают на код-ревью в любой команде.

### Грех №1: `ADD COLUMN ... DEFAULT <volatile>`
**Как делают обычно:**
```sql
ALTER TABLE orders ADD COLUMN created_at TIMESTAMP DEFAULT now() NOT NULL;
```
*Уровень блокировки:* `ACCESS EXCLUSIVE` + полный rewrite таблицы на диске.

**Как делать по-взрослому (Zero-Downtime паттерн):**
Разбиваем на 4 безопасных шага:
```sql
-- Шаг 1: Добавляем колонку как nullable без default (мгновенный апдейт каталога, 1 мс)
ALTER TABLE orders ADD COLUMN created_at TIMESTAMP;

-- Шаг 2: Выставляем дефолт только для будущих вставок (тоже мгновенно)
ALTER TABLE orders ALTER COLUMN created_at SET DEFAULT now();

-- Шаг 3: Фоново бэкфиллим старые строки батчами по 5000 строк (вне транзакции миграции)
-- UPDATE orders SET created_at = now() WHERE id BETWEEN 1 AND 5000;

-- Шаг 4: Когда NULL не осталось — навешиваем NOT NULL
ALTER TABLE orders ALTER COLUMN created_at SET NOT NULL;
```

---

### Грех №2: `CREATE INDEX` без модификатора `CONCURRENTLY`
**Как делают обычно:**
```sql
CREATE INDEX idx_orders_user_id ON orders (user_id);
```
*Уровень блокировки:* `SHARE`.  
Блокирует любые операции записи (`INSERT`, `UPDATE`, `DELETE`) во всю таблицу до тех пор, пока индекс не построится целиком. Если таблица весит 10M строк — запись заблокирована на 2–5 минут. Привет, накопление очереди запросов и тайм-аут!

**Как делать правильно:**
```sql
-- Важно: CONCURRENTLY нельзя запускать внутри транзакционного блока BEGIN...COMMIT
CREATE INDEX CONCURRENTLY idx_orders_user_id ON orders (user_id);
```
Postgres построит индекс в два прохода, не блокируя ни чтение, ни запись.

---

### Грех №3: Добавление Foreign Key напрямую
**Как делают обычно:**
```sql
ALTER TABLE order_items 
  ADD CONSTRAINT fk_order_items_product 
  FOREIGN KEY (product_id) 
  REFERENCES products(id);
```
*Уровень блокировки:* `ACCESS EXCLUSIVE`.  
PostgreSQL захватывает эксклюзивный лок и начинает последовательно сканировать миллионы строк дочерней таблицы, чтобы удостовериться, что битых ссылок нет. Все это время таблица намертво заморожена.

**Как делать правильно:**
Двухфазная валидация:
```sql
-- Шаг 1: Добавляем ограничение с флагом NOT VALID (проверяет только новые строки, лок берется на доли миллисекунды)
ALTER TABLE order_items 
  ADD CONSTRAINT fk_order_items_product 
  FOREIGN KEY (product_id) 
  REFERENCES products(id) 
  NOT VALID;

-- Шаг 2: Валидируем существующие исторические данные отдельной командой
-- Берет только слабый SHARE UPDATE EXCLUSIVE: и чтение, и запись продолжают работать!
ALTER TABLE order_items VALIDATE CONSTRAINT fk_order_items_product;
```

---

### Главный золотой закон: `SET lock_timeout`
Каждая миграция в вашей базе данных без исключения должна начинаться строкой:
```sql
SET lock_timeout = '3s';
```
Если в течение 3 секунд миграция не смогла получить блокировку (потому что кто-то читает таблицу), **она немедленно завершится с ошибкой**, а не встанет раком во главе очереди, блокируя собой сотни запросов клиентов. Лучше пусть упадет деплой в CI, чем ляжет весь продакшен!

## 3. Почему код-ревью не работает?

Мы написали внутренний регламент. Провели ретроспективу. Рассказали всем разработчикам про `ACCESS EXCLUSIVE`. 

Но через 3 месяца другой разработчик, перегруженный релизной спешкой в пятницу, написал:
```sql
ALTER TABLE subscriptions ADD CONSTRAINT uq_user_plan UNIQUE (user_id, plan_id);
```
И это снова вызвало блокирующий скан под эксклюзивным локом (потому что правильный паттерн — сначала `CREATE UNIQUE INDEX CONCURRENTLY`, а затем `ADD CONSTRAINT ... USING INDEX`).

Код-ревью — это человеческий фактор. На 50-й строчке диффа в Prisma или Alembic миграциях человеческий глаз «замыливается». Если задачу можно автоматизировать в CI/CD — ее **обязаны** выполнять роботы.

Мы изучили готовые решения:
- Часть утилит написана на Python/Ruby и требует тяжелого окружения или подключения к живой БД заказчика.
- Часть инструментов грешит наивным регулярным выражением (`grep -i "create index"`), которое выдает ложные срабатывания на комментариях или спотыкается на вложенных скобках.

Нам нужен был инструмент со следующими характеристиками:
1. **Чистый AST-анализ** SQL-синтаксиса (как компилятор, а не через RegExp).
2. **Нулевой runtime-оверхед:** запускается в CI за 200 миллисекунд без разворачивания баз данных и контейнеров.
3. **Автономность (Zero Dependencies):** один легковесный бинарник без 300 МБ в `node_modules`.
4. **Готовый авто-фикс:** не просто кричать «все сломалось», а давать разработчику готовый SQL-сниппет, который он копирует в PR.

Так родился **LockGuard**.

## 4. Как устроен LockGuard: от AST до блокировки PR

Мы упаковали анализатор в открытую CLI-утилиту и композитный **GitHub Action**.

```
[SQL Migration] 
     │
     ▼
[PostgreSQL DDL Lexer & Parser] (разбор в AST, очистка от комментариев и кавычек)
     │
     ▼
[Rule Engine: Top-8 Fatal Rules]
     │
     ├── Проверка 1: ADD COLUMN с volatile DEFAULT
     ├── Проверка 2: CREATE INDEX без CONCURRENTLY
     ├── Проверка 3: Foreign Key без NOT VALID
     ├── Проверка 4: ALTER COLUMN TYPE с rewrite таблицы
     ├── Проверка 5: Прямой UNIQUE constraint
     ├── Проверка 6: Опасный DROP TABLE/COLUMN
     ├── Проверка 7: VACUUM внутри транзакции
     └── Проверка 8: Отсутствие SET lock_timeout
     │
     ▼
[Verdict]: Нарушения найдены? 
     ├── ДА  ──> exit code 1 (Блокировка кнопки Merge в GitHub) + PR Comment с авто-фиксом
     └── НЕТ ──> exit code 0 (Зеленый CI, Zero-Downtime подтвержден)
```

### Как выглядит отчет бота в Pull Request:

Когда в репозиторий падает опасный PR, бот автоматически публикует разбор полетов:

![LockGuard PR Comment Preview](https://raw.githubusercontent.com/lockguard/lockguard/main/docs/assets/pr_comment_preview.png)

В комментарии разработчик видит:
* Какой именно лок запрашивается (`ACCESS EXCLUSIVE` или `SHARE`).
* Какие таблицы будут заморожены.
* Раскрывающийся спойлер `<details>` с **готовым безопасным кодом**, переписанным под zero-downtime استاندарт.

## 5. Как подключить к себе за 1 минуту

Вы можете проверить свои миграции локально прямо сейчас через `npx` (требуется только Node.js 18+):

```bash
npx lockguard check ./migrations
```

Если у вас нет папки миграций под рукой, можно запустить проверку встроенных катастрофических примеров:
```bash
git clone https://github.com/lockguard/lockguard.git
cd lockguard
npm test
npm run check
```

А чтобы подключить гейткипер в свой GitHub-репозиторий на каждый Pull Request, достаточно создать файл `.github/workflows/lockguard.yml`:

```yaml
name: LockGuard Migration Gatekeeper

on:
  pull_request:
    paths:
      - 'migrations/**'
      - 'prisma/migrations/**'
      - '**/*.sql'

jobs:
  audit-locks:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20

      # Подключаем гейткипер одной строкой:
      - name: Check PostgreSQL Locks
        uses: lockguard/action@v1
        with:
          migrations_dir: './migrations'
          format: 'github-pr-comment'
```

Для локальных экспериментов в проекте также встроен интерактивный веб-дашборд со **SQL Playground**:
```bash
npm start
# Доступен на http://localhost:3000
```
В нем можно вставить любой сырой SQL, посмотреть дерево блокировок и поэкспериментировать со сценариями.

## Заключение и чек-лист для проверки

Базы данных падают не от недостатка знаний, а от усталости и спешки перед релизом. Сделайте себе подарок к следующему четвергу — добавьте в ваш CI автоматический гейткипер блокировок.

**Краткий чек-лист перед каждым релизом DDL:**
- [ ] Стоит ли в начале миграции `SET lock_timeout = '3s';`?
- [ ] Создаются ли индексы строго через `CONCURRENTLY`?
- [ ] Добавляются ли внешние ключи через `NOT VALID` с последующим `VALIDATE CONSTRAINT`?
- [ ] Добавляются ли новые колонки без volatile-выражений в `DEFAULT`?
- [ ] Проверен ли PR автоматическим гейткипером?
